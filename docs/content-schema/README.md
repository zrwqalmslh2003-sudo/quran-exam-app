# عقد محتوى تطبيق قالون — Content Schema

> **المرحلة 2 (v1.15)** — تثبيت عقد البيانات قبل بناء طبقة التخزين (SQLite) أو المصدر البعيد (GitHub).
> ملاحظة: لا نبدأ بـ SQLite قبل مراجعة هذا العقد واعتماده لأن الجداول ستخزّن شكلاً نهائياً أو شبه نهائي من البيانات.

## الغرض

هذا العقد هو **المصدر الحقيقي (source of contract)** بين التطبيق والمحتوى البعيد مستقبلاً:
التخزين في SQLite تمثيل داخلي (implementation detail)، وشكل ملفات JSON هو ما يتفق عليه الطرفان.

## طبقات العقد الثلاث

```
manifest.json  →  فهرس كل الاختبارات + رقم الإصدار المركزي
   └── exam.json  →  اختبار واحد (id + version + questions[])
          └── questions[]  →  سؤال (النواة المشتركة أدناه)
```

## النواة المشتركة للسؤال

كل سؤال — مهما كان نوعه — يتكوّن من:

| الحقل | الحالة | النوع | ملاحظات |
| --- | --- | --- | --- |
| `id` | مطلوب | string | فريد داخل الاختبار |
| `type` | مطلوب | string | نقطة التمديد (extension point) |
| `prompt` | مطلوب | string | نص السؤال المعروض |
| `options` | شرطي | array<string> | مطلوب لأنواع الاختيار والآية |
| `correctAnswer` | شرطي | حسب النوع | مطلوب لأنواع الاختيار والآية |
| `category` | اختياري | string | تصنيف أعلى |
| `subcategory` | اختياري | string | باب/فرع |
| `difficulty` | اختياري | enum | `easy` `medium` `hard` `expert` (الافتراضي `easy`) |
| `explanation` | اختياري | string | يُعرض بعد الإجابة |
| `points` | اختياري | int ≥ 1 | وزن الدرجة (الافتراضي 1) |
| `order` | اختياري | int | ترتيب العرض (الافتراضي: ترتيب المصفوفة) |
| `reference` | اختياري | object/string | مرجع مصدري؛ محجوز لأسئلة الآيات |

### الأنواع المحددة الآن

| `type` | `options` | `correctAnswer` |
| --- | --- | --- |
| `single_choice` | مطلوب (≥ 2) | `integer` (فهرس، يبدأ من 0) |
| `ayah` | مطلوب (≥ 2) | `integer` (فهرس) — نفس شكل `single_choice` |
| `true_false` | اختياري | `boolean` |
| `multiple_choice` | مطلوب (≥ 2) | `array<int>` (فهارس، بلا تكرار) |

### أنواع محجوزة (تُثبَّت عند تفعيلها لاحقاً)

`ordering` · `fill_blank` · `image`

قاعدة **عدم الكسر**: أي نوع جديد **يضيف** الحقول فقط ولا يغيّر معنى الحقول الموجودة،
فلا يتطلب تعديلاً على الملفات القديمة.

## المحتوى الخاص بالقرآن / الآيات

أسئلة نوع `ayah` تتبع نفس النواة، وتُستخدم الحقول الاختيارية لوصف المرجع:

```json
{
  "id": "q003",
  "type": "ayah",
  "prompt": "إلى أي سورة تنتمي هذه الآية؟ «قُلِ الْحَمْدُ لِلَّهِ...»",
  "options": ["البقرة", "مريم", "الأنعام", "الكهف"],
  "correctAnswer": 3,
  "reference": {
    "kind": "ayah",
    "surahId": 18,
    "surahName": "الكهف",
    "verse": 1,
    "tafseer": "..."
  }
}
```

## قواعد التحقق من البيانات (Validation)

1. `schemaVersion` موجود ومساوٍ لإصدار العقد.
2. `exam.id` مطابق للمعرّف في `manifest.json` عند الوجود.
3. `exam.version` > 0، ويُقارن بالنسخة المحلية.
4. `questions[]` غير فارغة.
5. معرفات الأسئلة **فريدة** داخل الاختبار (تحقق تطبيقي — لا تعبَّر عنه في JSON Schema).
6. `correctAnswer` في حدود `options` (0 ≤ index < options.length) لتنسيق الاختيار.
7. `options` ≥ 2 لكل أنواع الاختيار.
8. `prompt` غير فارغ.
9. `difficulty` من القائمة المحددة.
10. حقل `type` من القائمة المذكورة (أو مُضاف موثّق).

## سلامة المحتوى البعيد

كل عنصر اختبار في `manifest.json` يجب أن يحتوي على الحقل `sha256`. وهو قيمة
سداسية عشرية بطول 64 محرفًا تمثل SHA-256 للبايتات الدقيقة لملف الاختبار.
ينزّل التطبيق الملف، يحسب البصمة قبل تخزينه، ويرفض التحديث كاملًا إذا لم
تتطابق البصمة. لا يُفعّل أي اختبار جديد عند فشل اختبار واحد.

## سياسة إصدارات العقد (schemaVersion)

- أي تغيير **يكسر** البنية: يرفع `schemaVersion` + توثيق Migration.
- أي تغيير تراكمي (إضافة حقل اختياري أو نوع جديد بلا كسر): لا يرفع `schemaVersion`،
  ويُوثّق في هذا الملف ليطّلع عليه باقي الفريق.
- التوافق مع المحتوى المثبّت حالياً يجب الحفاظ عليه كلما أمكن.

## شجرة التصنيفات البعيدة (Remote Category Tree — إضافة تراكمية)

> هذا وصف live 2026-09-10 — لا يرفع `schemaVersion` (كل الحقول اختيارية).

كل عنصر في `exams[]` يستطيع ربط الاختبار بشجرة تصنيفات (محلية أو بعيدة)
عبر حقول اختيارية:

| الحقل | النوع | المعنى | الشروط |
| --- | --- | --- | --- |
| `categoryId` | int ≥ 1 | مرجع category محلية فعالة | يجب أن يشير لمحلي فعال، أو يُرفض قبل أي تخزين |
| `subcategoryId` | int ≥ 1 | مرجع subcategory محلية فعالة | يجب أن يشير لمحلي فعال |
| `newCategoryName` | string | إنشاء category بعيدة | يُرفض إذا كان فارغاً/مبيّضاً |
| `newSubcategoryName` | string | إنشاء subcategory بعيدة تحت parent | تتطلب `categoryId` أو `newCategoryName` (أو `subcategoryId` كأب إلى category) |

### قواعد الهوية (Deterministic Identity)

- category محلية تُحل إلى reference ثابت `local:c:<id>`.
- category جديدة تُحل إلى `remote:c:<slug(name)>` حيث
  `slug = trim + استبدال كل مسافات باسم `_`` (اسم مطبّع، لا رقم عشوائي).
- **قيد مَعروف (غير محسوم عمدًا):** لا تطبيع لغوي للاسم العربي — الاسم
  يُستخدَم حرفيًا لتوليد المرجع. على مُعِدّي المحتوى استخدام إملاء موحَّد
  بالضبط عبر جميع تحديثات المانفيست لنفس التصنيف (لا تشكيل متغيّر، لا تثنية
  الهمزات/الألفات، لا تاء مربوطة مختلفة). أي اختلاف إملائي يُنشئ صنفًا
  بعيدًا ثانيًا صمتًا. يُتتبّع كعمل مؤجَّل في قسم «الديون التقنية» أدناه.
- اسم جديد مطابق لاسم category محلية قائمة → يحل **للمحلية** ولا ينشئ تكرراً.
- تكرار اسم جديد داخل نفس المانفيست → نفس المرجع (صف واحد).
- subcategory جديدة تحمل parent حتمي: `remote:sc:<parentRef>:<slug(name)>`.
